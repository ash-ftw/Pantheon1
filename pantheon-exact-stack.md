# Pantheon — Exact Tech Stack & Methods (B2B Edition)

This maps every module in the PRD to a specific, pinned, free/OSS tool and the method to use it — reframed from "internal cyber range" to "B2B: customer deploys their app, we test it in isolation" per the earlier redesign. Versions are current-stable as of writing; treat them as a starting pin, not a ceiling.

**PRD → B2B reframing, module by module:**
- "Cyber Range" templates → become **preset target-app catalog** (still useful — customers without their own app yet can spin up a vulnerable demo app to learn the platform) *plus* the new customer-app ingestion path.
- "Classroom Management" → deprioritized/optional; kept as a stretch module for teams who want internal training features, but not core to B2B.
- Everything else (Infrastructure Manager, Lab Builder, Application Import, AI Target Analysis, Endpoint Discovery, Simulation Library, AI Scenario Builder, Simulation Engine, Attack Graph, Observability, Defence Engine, Reporting) maps directly, with the execution model changed to range-cluster/tenant-cluster split.

## 3. Data Layer

| Concern | Exact Choice | Version (pin) | Method |
|---|---|---|---|
| Primary database | PostgreSQL | 16.x | One database, `tenant_id`/`org_id` column on every tenant-owned table — **not** separate schemas or databases per tenant (simpler migrations, acceptable isolation for row-level data since real isolation is enforced at the cluster/network layer already) |

## 4. Ingestion Pipeline (PRD: "Application Import" + "AI Target Analysis" + "Endpoint Discovery")

This is the module that changed most in the B2B redesign — PRD describes import as a manual multi-format upload; B2B version needs it fully automatic from a Git repo or compose file, with `.dockerignore` respected and no-Dockerfile apps auto-built.

| Concern | Exact Choice | Version (pin) | Method |
|---|---|---|---|
| Build (Dockerfile present) | Docker BuildKit (via `docker-py` invoking `docker build`) | Docker Engine 27.x | `DOCKER_BUILDKIT=1` always; multi-stage builds respected as-is from customer's Dockerfile |
| Build (no Dockerfile) | Cloud Native Buildpacks via **Paketo Buildpacks** + `pack` CLI | `pack` 0.35+, Paketo `base` builder (not `full`, not `tiny` — balance of language coverage vs. size for v1) | Invoked as a subprocess from `buildpacks_service.py`: `pack build <image> --builder paketobuildpacks/builder-jammy-base --path <repo_dir>` |
| `.dockerignore` handling | Docker's native build context exclusion (Dockerfile path) + Buildpacks' `.cnb-ignore`/project descriptor exclude (Buildpacks path) | native | Ingestion service checks for `.dockerignore` in repo root before either build path; if present, both engines are pointed at it (Buildpacks reads `.dockerignore` automatically as of recent Pack CLI versions) |
| Compose parsing | Manual parser against Compose Spec | PyYAML + own validator | `compose_translator.py` — extracts `services`, `depends_on`, `environment`, `ports`, `volumes`; each compose `service:` becomes one K8s `Deployment` + `Service` pair |
| Compose → K8s manifest generation | Hand-written Python manifest builder using `kubernetes` client's model classes (not a templating engine) | `kubernetes` 31.x models | Using the client library's typed models (`V1Deployment`, `V1Service`, etc.) instead of Jinja/YAML string templates avoids malformed-YAML bugs and gets validation for free |
| Git ingestion | GitPython, shallow clone | 3.1+ | Clone to ephemeral scratch dir under `/tmp` (or dedicated build-scratch volume), delete after image push regardless of success/failure |
| Image registry (self-hosted) | Docker Distribution (`registry:2`) OR Harbor | Harbor 2.11+ recommended once you need per-org auth/quotas; plain `registry:2` fine for Phase 0 | One registry per platform, but **repository namespaced per org** (`registry.local/org-<uuid>/app-<name>:tag`) — access control enforced by registry auth, not by having separate registry instances |
| Secrets extraction (compose `.env`/`environment:`) | Custom logic in `compose_translator.py` | — | Any `environment:` value matching common secret-name patterns (`*_KEY`, `*_SECRET`, `*_PASSWORD`, `*_TOKEN`) OR anything sourced from `.env` is placed into a K8s `Secret` and referenced via `envFrom`/`valueFrom`, never left as a literal in the `Deployment` spec |
| Language/framework detection (feeds "AI Target Analysis") | Paketo's own detection phase (already runs during buildpacks build) + supplement with `linguist`-style heuristics for metadata display | `go-enry` (Python binding: `enry` via subprocess, or pure-Python fallback with file-extension heuristics) | Buildpacks detection tells you what it *built with*; enry/heuristics fill in "here's what we found" for the UI even on the Dockerfile-present path where Buildpacks didn't run |
| OpenAPI/Swagger discovery ("Endpoint Discovery") | `prance` + `openapi-spec-validator`, checked at common paths (`/openapi.json`, `/swagger.json`, `/api-docs`) via safe internal HTTP probe post-deploy | — | Probe runs from inside the tenant cluster (not the range cluster) immediately after deploy, before any attack scenario — this is reconnaissance on the customer's own newly-deployed app, not an attack |

## 6. Route Broker (new, safety-critical — replaces PRD's implicit "everything in one lab" model)

| Concern | Exact Choice | Version (pin) | Method |
|---|---|---|---|
| Route object | K8s `Ingress` or Traefik `IngressRoute`, created per test run | native / Traefik 3.x | One route = one rule: `range-cluster attacker pod → tenant-namespace/target-service:port`, nothing else |
| TTL enforcement | Celery beat periodic task scanning route expiry + K8s object itself carries an annotation with expiry timestamp | Celery 5.4+ (beat scheduler) | `route_broker.py` writes the route with an `expires-at` annotation; a periodic task (`celery beat`, every 30s) sweeps and deletes anything past expiry, independent of whether the test run "cleanly" finished |
| Kill switch | Direct API call from `route_broker.py` — delete the K8s route object immediately, don't wait for the periodic sweep | — | Exposed as `DELETE /test-runs/{id}/route`; frontend kill-switch button calls this directly, not through Celery, so it's synchronous and immediate |
| Audit trail | Every route create/delete written to `audit_log` table (Postgres) in the same transaction/request as the K8s API call | — | If the K8s call fails, the audit entry still records the attempt — audit log is append-only regardless of success |
| Cross-cluster credential handling | Range cluster's outbound requests carry no tenant cluster credentials at all — routing is done by the **tenant cluster** exposing the route, not by the range cluster reaching in with credentials | — | This is the actual safety property: the tenant cluster decides what's reachable; the range cluster just has a URL it's allowed to hit, nothing more |

## 7. Attack Orchestration (PRD: "Simulation Engine" + "AI Scenario Builder" + "Simulation Library")

| Concern | Exact Choice | Version (pin) | Method |
|---|---|---|---|
| Scenario definitions | Structured JSON/YAML, validated by Pydantic models, **not arbitrary code** | Pydantic v2 | Every scenario (preset or customer-authored "custom") is `{target, method, payload_category, concurrency, duration, expected_signals}` — matches PRD's "AI never produces unrestricted exploits" principle, extended to also constrain human-authored custom scenarios |
| Preset scenario library | Hand-authored Pydantic scenario definitions, one file per category under `app/scenarios/` | — | Directly implements PRD's Simulation Library list: brute force, credential guessing, SQLi resilience, XSS reflection, auth abuse, BOLA, API abuse, cache pressure, traffic flood, service/dependency/DB failure, network partition, resource exhaustion, lateral-movement simulation, multi-stage chains |
| HTTP-based attack execution | httpx (async) | 0.27+ | Attacker pods run a small async Python worker using httpx for all "controlled HTTP request" style scenarios (brute force, SQLi resilience, XSS reflection, API abuse) |
| Load/traffic simulation | Locust (used as a library, not just its CLI/web UI) | 2.31+ | `LocustRunner` invoked programmatically from the attacker pod for traffic flood / cache pressure scenarios, results streamed back via Redis pub/sub → WebSocket instead of Locust's own web UI |
| Failure injection (service/dependency/DB failure, network partition) | Chaos Mesh (K8s-native chaos engineering) | 2.7+ | Applied in the **tenant** namespace directly (this isn't an "attack" needing the route broker — it's a controlled fault injection the customer's own platform triggers on their own workloads), via Chaos Mesh CRDs (`PodChaos`, `NetworkChaos`, `StressChaos`) |
| Resource exhaustion simulation | Chaos Mesh `StressChaos` | 2.7+ | Same mechanism as above |
| AI scenario generation | LLM call (provider TBD — see Open Questions) constrained to output the same Pydantic scenario schema | — | Prompt instructs the model to fill in a fixed schema; response is parsed and **re-validated** against the Pydantic model before it's allowed to run — never trust the LLM's output as executable directly |
| Real-time progress streaming | Redis pub/sub (attacker pod publishes) → FastAPI WebSocket endpoint (subscribes, forwards to frontend) | Redis 7.x native pub/sub | Decouples the attacker pod (which may be on the range cluster, physically separate) from the backend's WebSocket layer — pod never talks to the frontend directly |
| Simulation guard (allowlist) | Explicit allowlist of permitted scenario "kinds," checked in `app/safety/simulation_guard.py` before any run — including AI-generated and custom scenarios | — | Directly implements PRD's safety rules: no real malware, persistence, credential theft, reverse shells, ransomware, privilege escalation, data exfiltration, internet scanning, or real exploit chains — enforced as code, not just as policy text |

## Summary — What's Genuinely New vs. What the PRD Already Implied

| PRD said | B2B stack does instead |
|---|---|
| "Application Import" via manual format upload | Fully automatic ingestion: Git URL or compose file in, Buildpacks/Docker build out, deployed without customer touching K8s |
| "Everything happens inside isolated Docker containers and Kubernetes namespaces managed by Pantheon" (implies one shared lab) | Real tenant/range cluster split, Route Broker enforcing scoped ephemeral access instead of shared-namespace isolation |
| "Pantheon only operates against internal registered lab services" | Same principle, now enforced as: attacker pods can *only* ever reach whatever Route Broker has explicitly opened, nothing else, ever |
| Classroom Management as a core module | Optional/deprioritized — B2B customers are companies testing their own apps, not students; kept as a stretch feature list, not core path |
| "AI never produces unrestricted exploits" | Same principle, extended: **all** scenarios (AI-generated or human-authored custom) go through the same Pydantic-schema + allowlist gate — the AI isn't a special case, it's just one more untrusted input source |
